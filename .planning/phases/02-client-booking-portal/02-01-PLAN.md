<task type="auto">
  <name>Task 1: Criar migration Phase 2</name>
  <files>supabase/migrations/20260601000001_phase2_schema.sql</files>
  <action>
Criar o arquivo de migration exatamente conforme especificado na RESEARCH.md, Decisão 2 (SQL exato) e Decisão 4 (RLS anon). A migration deve conter 5 seções nesta ordem:

SECTION A — Extensão btree_gist:
  `CREATE EXTENSION IF NOT EXISTS btree_gist;`
  Deve vir ANTES da constraint. Sem ela o UUID não tem suporte ao access method GIST.

SECTION B — Exclusion constraint (double-booking prevention):
  ```sql
  ALTER TABLE public.appointments
    ADD CONSTRAINT appointments_no_overlap
    EXCLUDE USING gist (
      barber_id WITH =,
      tsrange(start_time, end_time, '[)') WITH &&
    )
    WHERE (status != 'CANCELLED');
  ```
  Usar `'[)'` (semi-aberto) — NÃO `'[]'`. Slots contíguos (fim=início do próximo) NÃO devem colidir.
  Escopo por `barber_id WITH =`: dois barbeiros diferentes podem ter o mesmo horário.

SECTION C — UNIQUE constraint em clients para upsert por WhatsApp:
  ```sql
  ALTER TABLE public.clients
    ADD CONSTRAINT clients_barbershop_whatsapp_unique
    UNIQUE (barbershop_id, whatsapp_number);
  ```
  Esta constraint permite o `upsert ... onConflict: 'barbershop_id,whatsapp_number'` na Server Action.

SECTION D — DROP NOT NULL em created_by:
  ```sql
  ALTER TABLE public.appointments
    ALTER COLUMN created_by DROP NOT NULL;
  ```
  Backward-compatible: dados da Fase 1 têm created_by preenchido. Apenas remove a obrigatoriedade para novos INSERTs do portal.

SECTION E — 6 políticas RLS SELECT para role anon:
  1. `anon_barbershops_select` ON public.barbershops FOR SELECT TO anon USING (true)
  2. `anon_services_select` ON public.services FOR SELECT TO anon USING (is_active = true)
  3. `anon_barbers_select` ON public.barbers FOR SELECT TO anon USING (is_active = true)
  4. `anon_working_hours_select` ON public.working_hours FOR SELECT TO anon USING (is_active = true)
  5. `anon_appointments_select` ON public.appointments FOR SELECT TO anon USING (status != 'CANCELLED')
  6. `anon_barber_services_select` ON public.barber_services FOR SELECT TO anon USING (true)

  NOTA: INSERT de clients e appointments usa adminClient (service role) na Server Action — não requer políticas INSERT para anon. A `anon_client_insert` da Fase 0 pode coexistir sem conflito.

Incluir comentário de cabeçalho documentando o propósito de cada seção.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-02-01 | Tampering | appointments — exclusion constraint | mitigate | Constraint GIST parcial com WHERE (status != 'CANCELLED') previne double-booking mesmo em race conditions de milissegundos |

| T-02-SC | Tampering | npm/pip/cargo installs | accept | Nenhum pacote novo nesta migration — apenas SQL e CLI Supabase já instalado |
