Criar o arquivo de migration com o seguinte conteúdo exato:

Cabeçalho padrão do projeto (ver analog phase2):
```
-- ============================================================
-- BarberFlow Phase 3 — QR Check-In Schema
-- Migration: 20260602000001_phase3_schema.sql
--
-- MULTI-TENANCY CONTRACT:
--   used_qr_tokens não tem barbershop_id próprio — isolamento via FK
--   para appointments.barbershop_id. RLS usa subquery nessa coluna.
-- ============================================================
```

SECTION A — Criar tabela used_qr_tokens:
- id UUID PRIMARY KEY DEFAULT gen_random_uuid()
- appointment_id UUID NOT NULL REFERENCES public.appointments(id) ON DELETE CASCADE
- token_hash TEXT NOT NULL — SHA-256 hex do token completo (64 chars, nunca o token raw)
- consumed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

Nota: NÃO incluir issued_at/expires_at na tabela — esses dados já estão encodados no token. Manter schema mínimo.

SECTION B — Índices:
- UNIQUE INDEX used_qr_tokens_token_hash_idx ON (token_hash) — guard atômico da race condition
- INDEX used_qr_tokens_appointment_id_idx ON (appointment_id) — FK lookups

SECTION C — RLS:
- ALTER TABLE public.used_qr_tokens ENABLE ROW LEVEL SECURITY;
- Policy "tenant_read_used_qr_tokens" FOR SELECT TO authenticated: USING com subquery appointments WHERE barbershop_id = (auth.jwt() -> 'app_metadata' ->> 'barbershop_id')::UUID
- NENHUMA policy para INSERT/UPDATE/DELETE autenticado ou anon — todo write vai via adminClient (service role) que bypassa RLS
- Comentário explicando por que sem INSERT policy: "Writes via adminClient (service role) bypass RLS — no anon/authenticated INSERT policy needed"
