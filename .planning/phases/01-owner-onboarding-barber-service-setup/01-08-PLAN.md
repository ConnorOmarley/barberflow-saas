```typescript
async function checkConflict(supabase, barberId, startTime, endTime): Promise<boolean> {
  const { data } = await supabase
    .from('appointments')
    .select('id')
    .eq('barber_id', barberId)
    .neq('status', 'CANCELLED')
    .lt('start_time', endTime)   // existing start < new end
    .gt('end_time', startTime)   // existing end > new start
    .limit(1)
  return (data?.length ?? 0) > 0
}
```

Export async function createAppointment(data: {
  barber_id: string
  service_id: string
  client_id?: string
  new_client?: { full_name: string; whatsapp_number: string }
  start_time: string  // ISO string
  notes?: string
})

Implementation:
1. getClaims → validate auth → extract barbershop_id and userId
2. Validate: barber_id and service_id provided; either client_id or new_client provided
3. Fetch service to get duration_minutes: supabase.from('services').select('duration_minutes').eq('id', data.service_id).single()
4. Compute end_time = new Date(data.start_time + duration_minutes * 60000).toISOString() (server-side — never accept end_time from client)
5. If new_client: INSERT into clients { barbershop_id, full_name: new_client.full_name, whatsapp_number: new_client.whatsapp_number, whatsapp_opt_in: false } → get new client_id
6. Conflict check: SELECT id FROM appointments WHERE barber_id = ? AND status != 'CANCELLED' AND start_time < end_time AND end_time > start_time LIMIT 1. If conflict: return { error: 'Horário indisponível. O barbeiro já tem um agendamento nesse horário.' }
7. INSERT appointments: { barbershop_id, barber_id, service_id, client_id, start_time, end_time, status: 'CONFIRMED', notes: data.notes ?? null, booking_source: 'manual', created_by: userId }
8. revalidatePath('/dashboard') + revalidatePath('/agenda')
9. Return { data: appointment } | { error }

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ClientCombobox (browser) → clients query | RLS enforces barbershop_id automatically — browser client cannot access other tenants' clients |
| AppointmentDrawer → createAppointment | barbershop_id nunca aceito como parâmetro; conflict check executado server-side |
| CancelDialog → cancelAppointment | appointment ownership verificado via barbershop_id do JWT no Server Action |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-19 | Tampering | createAppointment — end_time manipulation | mitigate | end_time computado server-side de services.duration_minutes — cliente não pode passar end_time |
| T-01-20 | Tampering | Double-booking race condition (app-layer only) | accept (documented) | Phase 1 tem apenas conflict check app-layer; dois requests simultâneos dentro de ms podem bypassar. Phase 2 adiciona GIST exclusion constraint. Documentado como known limitation. |
| T-01-21 | Information Disclosure | ClientCombobox — client search expõe dados | accept | RLS garante que apenas clients do mesmo barbershop são retornados; busca por nome/WhatsApp é funcionalidade intencional do owner/barber |
| T-01-22 | Tampering | new_client inline create — whatsapp_opt_in | mitigate | Sempre false no servidor (createAppointment); cliente nunca pode setar opt_in=true via este fluxo; opt-in UI é Phase 5 |
</threat_model>
